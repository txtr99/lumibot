CORE ISSUE
──────────────────────────────────────────────────────────────────────────────────
repair_position_desync() zeros virtual positions while bracket orders remain active
on exchange, creating orphaned orders that can cause:
  ✗ Real fills not tracked
  ✗ P&L calculation errors
  ✗ Data inconsistencies
  ✗ Memory leaks

7 VULNERABLE CODE PATTERNS
──────────────────────────────────────────────────────────────────────────────────

Pattern 1: Exception Silencing (tools/bracket_order_manager.py:2204-2210)
          try: cancel() except: log() → position zero ALWAYS executes

Pattern 2: No Cancel Confirmation (tools/bracket_order_manager.py:301-320)
          Cancel API call → return True/False, never verify TERMINAL state

Pattern 3: No Bracket Cleanup (tools/bracket_order_manager.py:368-390)
          cancel_bracket() → orders cancelled, dict entry NEVER removed

Pattern 4: No Thread Safety (lumibot/tools/virtual_position_tracker.py)
          reset() and execute_order() race on shared dict without locks

Pattern 5: State Divergence (BracketOrderManager vs EnhancedStrategyState)
          Two separate state machines tracking same position + brackets

Pattern 6: No Atomic Boundary (tools/bracket_order_manager.py:2185-2228)
          Cancel + Zero separate operations, can't rollback on failure

Pattern 7: No Fill Validation (tools/bracket_order_manager.py:_process_fills)
          Fill applied without checking position exists or matches direction


CRITICAL PATH FAILURES
──────────────────────────────────────────────────────────────────────────────────

Flow 1: Exception Silencing → Orphaned Bracket
  repair_position_desync()
    └─ cancel_brackets_for_strategy() → EXCEPTION
      └─ CAUGHT: log warning
      └─ CONTINUE: state.tracker.reset()  ← PROBLEM: executes anyway
      └─ RESULT: Position FLAT, bracket ACTIVE ✗

Flow 2: No Cancel Confirmation → Zombie Orders
  _cancel_order(order_id)
    └─ API response: {"success": False}
      └─ RETURN False
      └─ Position zeroed despite cancel failure ✗
      └─ But order IS cancelled on exchange (network loss)
      └─ RESULT: Code thinks failed, order is terminal ✗

Flow 3: Concurrent Access → Data Corruption
  Thread 1: repair()          Thread 2: poll()
    └─ reset()   ─────────┬──────── execute_order()
    └─ clear()   ─────────│
                          └─ write to cleared dict ✗
